# 전광판 동적 레이아웃 설계 (Issue #448)

## 배경

파티룸 데스크탑 화면의 비-cinema 모드에서 브라우저 가로 폭을 줄이면 중앙에 배치된 전광판(`PartyroomDisplayBoard`)이 오른쪽 사이드 패널(채팅/정보 탭, 고정 400px)에 가려진다.

원인: `src/widgets/partyroom-page-desktop/room.component.tsx`에서 비-cinema 모드의 전광판 컨테이너가 `left-1/2 -translate-x-1/2`로 뷰포트 정중앙에 고정폭(512px 콘텐츠 + 좌우 40px 패딩 = 592px)으로 배치될 뿐, 오른쪽 400px 패널의 존재를 전혀 고려하지 않는다. 뷰포트 폭이 약 1392px 미만이면 두 요소가 겹치기 시작하며, DOM 순서상 오른쪽 패널이 나중에 렌더링돼 위를 덮는다.

cinema 모드는 이미 이 문제를 풀어놓은 상태다: `boardWidth = window.innerWidth - 400 - 80`을 resize 이벤트마다 재계산해 오른쪽 패널 폭을 전광판 폭 계산에 반영한다(`room.component.tsx:70-81`). 단, 이 로직은 `cinemaView`일 때만 동작한다.

## 목표

비-cinema 모드에서도 전광판이 오른쪽 사이드 패널에 가려지지 않도록, 뷰포트 폭에 따라 위치와 크기가 동적으로 조정되게 한다.

## 동작 사양

뷰포트 폭(`vp`)에 따라 3단계로 연속적으로 전환된다.

| 단계         | 뷰포트 폭 조건      | 전광판 콘텐츠 폭                                             | 위치                                              |
| ------------ | ------------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| 1. 평소      | `vp >= 1392`        | 512px 고정                                                   | 뷰포트 정중앙 (기존과 동일)                       |
| 2. 좁아짐    | `1032 <= vp < 1392` | 512px 고정 (유지)                                            | 오른쪽 패널에 밀착(`right: 400px`), 왼쪽으로 밀림 |
| 3. 매우 좁음 | `vp < 1032`         | `max(320, vp - 440 - 80)` = `max(320, vp - 520)` (점점 축소) | 계속 오른쪽 패널에 밀착, 왼쪽 여백(40px) 유지     |

### 상수

```
RIGHT_PANEL   = 400   // 오른쪽 채팅 패널 고정 폭
MARGIN        = 40    // 컨테이너 내부 좌우 패딩 (px-[40px], 기존 관례)
LEFT_BOUND    = 40    // 3단계에서 컨테이너 좌측 끝이 화면 왼쪽 가장자리로부터 확보할 최소 여백
DEFAULT_CONTENT = 512 // 평소 전광판 콘텐츠 폭
MIN_CONTENT     = 320 // 축소 하한
```

### 계산식

```
containerWidth(vp) =
  vp >= 1032 ? 592                         // DEFAULT_CONTENT(512) + 2*MARGIN(80), 1·2단계 공통
             : Math.max(400, vp - 440)     // 400 = MIN_CONTENT(320) + 2*MARGIN(80)
                                            // 440 = RIGHT_PANEL(400) + LEFT_BOUND(40)

rightOffset(vp) = Math.max(400, (vp - containerWidth(vp)) / 2)
  // vp >= 1392: (vp-592)/2 >= 400 → 중앙정렬과 동일한 값 (1단계)
  // vp <  1392: 400 으로 clamp → 오른쪽 패널에 밀착 (2·3단계)

boardWidth(vp) = containerWidth(vp) - 80   // DisplayBoard 에 전달되는 콘텐츠 폭
```

**경계값 유도.** `containerWidth`의 두 경계값(`1392`, `1032`)은 임의 상수가 아니라 위 계산식 자체에서 나온다:

- **1392 (1↔2단계):** 정중앙 배치(`containerWidth=592`)의 우측 끝이 오른쪽 패널에 닿기 직전 지점. `(vp+592)/2 = vp-400` → `vp=1392`.
- **1032 (2↔3단계):** 오른쪽 패널에 밀착한 채(`containerWidth=592` 유지) 좌측 끝이 `LEFT_BOUND(40)`까지 줄어드는 지점. 좌측 끝 = `(vp-400)-592 = vp-992`. `vp-992=40` → `vp=1032`.
- **840 (3단계 축소 하한):** `vp-440 = 400`(=MIN_CONTENT+2·MARGIN) → `vp=840`. 이 아래로는 `containerWidth`가 400에서 더 줄지 않는다.

각 경계에서 인접 구간의 공식이 동일한 값을 낸다(대수적으로 확인됨. 자체 리뷰 중 초안의 계산 오류를 발견해 상수를 `LEFT_BOUND` 도입으로 수정함 — 최초 유도 시 좌측 여백을 누락해 1032 대신 992로 잘못 계산했었다):

- `vp=1392`: `containerWidth=592`(1032 이상이므로), `rightOffset = max(400, (1392-592)/2) = max(400,400) = 400` — 여기서 한 단위라도 더 커지면(`vp=1393`) `(vp-592)/2 > 400`이 되어 자연스럽게 중앙정렬 값으로 이어짐.
- `vp=1032`: 2단계 `containerWidth=592`(경계 포함), 3단계 공식 `Math.max(400, 1032-440) = Math.max(400,592) = 592` — 정확히 일치.
- `vp=840`: `Math.max(400, 840-440) = Math.max(400,400) = 400` — 이 지점에서 하한 적용 시작, `boardWidth=320`(MIN_CONTENT).

## 하한 처리

`vp < 840`이 되면 `containerWidth`가 400(콘텐츠 320)에서 더 줄어들지 않는다. `rightOffset`은 계속 400으로 유지되므로(오른쪽 패널에 계속 밀착), 좌측 끝은 `vp - 800`이 되어 `vp < 840`부터 `LEFT_BOUND(40)`보다 작아지기 시작하고, `vp < 800`이면 화면 왼쪽 가장자리(0)를 넘어선다. 이는 매우 좁은 데스크톱 창(840px 미만)에서만 발생하는 극단적 상황으로, 원 이슈가 오른쪽 패널 문제만 다루므로 이번 작업 범위 밖으로 명시한다.

## 구현 방식

- `room.component.tsx`의 기존 `useEffect`(현재 `if (!cinemaView) return`으로 cinema 전용)를 확장해, `!cinemaView`일 때도 위 계산식으로 `boardWidth`와 새 state `boardRightOffset`을 계산한다. cinema 모드의 기존 공식(`innerWidth - 400 - 80`, 고정 `right-[400px]`)은 변경하지 않는다.
- 전광판 컨테이너의 포지셔닝을 `left-1/2 -translate-x-1/2`(정적 중앙 고정)에서 동적 `right: <boardRightOffset>px`(인라인 style)로 교체한다. `left`/`transform` 클래스는 제거한다.
- `Video` 컴포넌트는 이미 `width` prop을 받아 `height = width * (288/512)`로 비율을 유지해 계산하므로, 3단계(축소)에서 별도 처리가 필요 없다.
- 리사이즈 리스너는 기존과 동일하게 `window.addEventListener('resize', ...)` + `useEffect` cleanup 패턴을 그대로 재사용한다 (새 메커니즘 도입 없음).
- `containerWidth`/`rightOffset` 계산은 순수 함수로 분리해 유닛 테스트 대상으로 만든다 (컴포넌트 밖, 예: `room.component.tsx`와 같은 디렉터리의 헬퍼 모듈).

## 범위 밖

- 왼쪽 아이콘 사이드바(`left-[40px]`)와의 충돌 방지: 840px 미만의 매우 좁은 데스크톱 창에서만 이론상 발생. 이번 이슈는 오른쪽 패널 문제만 다루므로 다루지 않는다.
- cinema 모드: 변경 없음.
- 모바일 트리(`widgets-mobile`): 별도 컴포넌트 트리이므로 영향 없음.

## 테스트 전략

- 분리한 순수 함수(`containerWidth`, `rightOffset`, `boardWidth`)에 대한 유닛 테스트로 경계값(839/840/1031/1032/1391/1392 등)에서의 계산 결과를 검증한다.
- 수동 검증: 브라우저 폭을 1920 → 1400 → 1392 → 1200 → 1032 → 900px로 단계적으로 줄이며 전광판이 오른쪽 패널과 겹치지 않고, 단계 전환 시 시각적 점프가 없는지 확인한다.
