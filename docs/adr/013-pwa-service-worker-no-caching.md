# ADR-013: PWA 서비스워커는 아무것도 캐싱하지 않는다

- **상태**: ✅ 채택·구현 완료 (설치 + Web Push 배포됨)
- **일자**: 2026-06-16 (설계) / 2026-07 (구현·prod 반영)
- **관련**: [#404](https://github.com/pfplay/pfplay-web/issues/404), PR #424(Phase A 설치)·#425(Phase D 푸시)·#459(아이콘)
- **관련 코드**: `public/sw.js`, `src/app/manifest.ts`, `src/features/push-notification/`

## 배경

PWA 전환의 목표는 두 가지였다 — **홈 화면 설치(standalone)** 와 **Web Push**.
일반적인 PWA 레시피(`next-pwa`, `serwist`, Workbox)는 여기에 **오프라인 캐싱**을 기본으로 끼워
넣는다. 문제는 pfplay 가 realtime-heavy 앱이라는 점이다.

- 재생 위치·DJ 큐·presence·채팅은 전부 WS 로 흐르고, 서버가 유일한 권위다.
- 이 레포에는 이미 "클라이언트가 낡은 서버 상태를 믿어서" 생긴 결함 계열이 있다
  (유령 재생, 재연결 시 resync 부재).
- 서비스워커가 API 응답을 캐싱하면 그 계열을 **증폭**시킨다. 사용자는 새로고침해도 낡은 상태를
  보게 되고, 원인은 네트워크 탭에 나타나지 않는다(요청이 아예 나가지 않으므로).

점검 모드도 걸린다. 점검은 Edge Config rewrite 로 전환되는데, 서비스워커가 앱셸을 서빙하면
점검 화면으로 넘어가지 않는 창이 생긴다.

## 결정

**서비스워커를 직접 작성하고, 캐싱을 전혀 하지 않는다.** 라이브러리를 쓰지 않는다.

`public/sw.js` 의 책임은 정확히 두 가지다.

1. **설치 가능성 충족** — 일부 브라우저가 설치 프롬프트 조건으로 `fetch` 리스너 존재를 요구한다.
   따라서 **아무 일도 하지 않는 빈 `fetch` 핸들러**를 둔다. 응답을 가로채지 않으므로 캐싱도,
   셸 서빙도 없다.
2. **Web Push 수신·표시** — `push` 이벤트에서 payload 를 파싱해 알림을 띄우고, 클릭 시 지정
   URL 로 이동시킨다.

`install` 에서 `skipWaiting()`, `activate` 에서 `clients.claim()` 을 호출해 새 버전이 즉시
활성화되게 한다. 캐시가 없으므로 버전 간 정합성 문제도 없다.

> ⚠️ **빈 `fetch` 핸들러를 "죽은 코드" 로 오해해 지우지 말 것.** 지우면 일부 브라우저에서
> 설치 프롬프트가 사라진다. `sw.js` 주석에도 같은 경고가 있다.

## 결과

**얻은 것**

- 설치·푸시라는 목표를 달성하면서 stale 위험을 0 으로 유지했다.
- 점검 모드 게이팅과 충돌하지 않는다.
- 서비스워커 관련 디버깅 표면이 거의 없다(캐시 무효화·버전 스큐 문제 자체가 없음).

**받아들인 비용**

- 오프라인에서는 아무것도 동작하지 않는다. 실시간 파티룸 앱에서 오프라인 사용은 의미가 없다고
  판단했다.
- 반복 방문 로딩 체감 개선이 없다(앱셸 캐싱을 포기했으므로). 필요해지면 **정적 자산에 한해**
  좁게 도입하되, API 응답 캐싱은 이 ADR 을 뒤집는 새 ADR 없이는 하지 않는다.

## 운영 메모

푸시 발송은 백엔드 게이트에 묶여 있다 — `WEB_PUSH_ENABLED` 와 VAPID 키가 설정돼야 실제로
나간다(미설정 시 fail-closed). 프론트에서 구독이 성공해도 알림이 오지 않는다면 이 게이트를 먼저
확인한다.
